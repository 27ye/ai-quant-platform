## C 已准备的执行顺序

1. 核对最终 SHA、来源与完整文件哈希，校验新包 raw/normalized/manifest/独立回读及旧差异；用新输出目录保存证据，不覆盖旧批次。
2. 三股为 **600519 / 000001 / 300750**，固定窗口 **2025-07-04～2026-08-31**。每股运行 `{}`、MA10/30、MA20/60+本金200000+成本0.002+滑点0.001，共9组。包覆盖不足则报告，不悄悄移动窗口。
3. 先以同一规范化输入直接调用 C，再跑正式 POST，记录真实 backtest_id；重建数据库 engine/session 后 GET 完整 c_result，比较全部数值/类型/哈希/预热/本金/成交/三曲线。POST 的五字段参数投影与 C 完整配置按已有契约分别比较，不把合法包装差异当数值错误。
4. 验旧结果 exact=false、新结果 exact=true、历史读取不调用 Provider/Quant/News/LLM；新包九组与旧迁移夹具分开。核对默认 AI 不被参数回测污染。
5. 单独复验 V1 冻结基线：33分、24条订单、12次往返、403点；不要求新V2窗口复制这些计数。
6. 发布绑定**完整组合 SHA + 数据批次 + manifest/file hash**的 C 量化结论；列出通过项、差异和剩余阻塞，再更新最终评审。若算法、服务、持久化、依赖或数据有新变动，评估并复验受影响项；旧签字不自动覆盖新 SHA。

已有 `scripts/validate_v2_c_acceptance.py` 支持新包目录、新输出目录和独立可信 `--expected-hashes` 文件。它只完成文件/直接计算/JSON回读阶段，不代替 HTTP 和真实 MySQL。旧 `C_V2_ACCEPTANCE_REQUESTS.json` 可参考9组请求参数，但其中旧批次来源元信息不能作为新包凭据。
