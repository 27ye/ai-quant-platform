## 4. 四类哈希及精度边界

| 标识 | 对象 | 验收注意 |
|---|---|---|
| 文件 SHA-256 | 交付文件原始字节 | JSON 缩进或数值表示变化可能改变文件哈希 |
| C `data_hash` | `input_snapshot` 除 sha256 外的规范内容 | 包括实际 long 条预热、窗口内 bars、可选列、data_mode 等；保留 C 返回值 |
| D `context_hash` | 规范化后的 AI 结构化上下文 | 包含量化投影、新闻、来源和时间等，不是 C 全量 bars 的哈希 |
| Git SHA | 代码提交 | 算法版本和数据版本需另外记录；本地未提交文件还需内容校验清单 |

这些标识计算对象不同，不要求互相相等。C 的 `data_hash` 应与同一结果中的 `input_snapshot.sha256` 相同；历史回看必须保留原上下文、输入及哈希。

PR #10 的 `normalize_analysis_context` 将 AI 上下文数值处理为 15 位有效数字、负零转零，随后 Prompt 和数据库保存均使用该上下文。这是 D 的 AI 边界转换，不是 C 计算精度规则，不能应用到 C 的原始结果或 input_snapshot 后仍保留旧哈希。

D 的 `snapshot_status=complete` 只证明 AI 上下文具有它的必需字段；该上下文含技术指标末值、评分和默认回测摘要，并不包含 C 全量行情、全部订单/曲线或完整 QuantConfig。B 仍需独立保存 C 的完整输入和回测结果。C 到 AI 的投影对账使用 D 的字段及数值规范，不能要求舍入后的 AI 数字与未舍入的 C 浮点数逐字节相等。

B 的行情 4/2/6 规范发生在输入 C 之前；C 的订单、曲线、权益和输入快照不再按摘要表精度舍入。API 直接计算和 MySQL 回读比较需使用同一规范化输入及实际 data_mode。D 的 AI 快照回读证据不证明 C 的全精度 JSON 在 MySQL 已通过；如真实回读发现数值或哈希变化，B/C 应确定保存方式并复验，不静默放宽比较或截断数值。

## 5. 来源与时间边界

- 请求内 provenance：记录本次返回给分析路径的数据来源，由 B/D 在实际 query 后捕获。
- 持久同步状态：描述缓存表的同步记录，由 B 管理；后续刷新不得改变旧报告或回测的已存来源。
- C `data_mode`：快照中的现有输入标记，不是完整来源证据，不能仅凭此标记声称数据真实或实时。
- 行情日期：使用 bar 的 `trade_date` 及实际区间；不使用报告创建时间替代。
- PR #10 当前 `data_as_of` 和 `provenance.retrieved_at`：由上下文组装时间赋值，不是 provider 抓取时间的独立证明。

若 B 提供 provider 抓取时间、持久同步时间及数据版本，应明确各自字段和事实来源。C 不根据最新 stock_daily 或当前 stock_daily_sync 反推历史来源，也不随意改写 data_mode 使离线验证与服务记录不一致。
