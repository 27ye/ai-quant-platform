## 决策一：C接受本轮方案A，暂不要求v9

支持按股票整段刷新缓存，由D确认产品方案及实施者。C不要求本轮为了逐行source新增v9；也不将逐行source单独视为复权一致性证明。

1. 范围覆盖该股票既有有效缓存区间与本次请求预热/计算窗口的并集。新批次必须保持一个真实来源及一致qfq口径。适用于东财→腾讯及腾讯→东财；既有来源不明的缓存不能仅重贴标签。
2. **先完整取数和校验，再原子发布行情及其成功来源/范围记录。** 不先删除旧缓存；取数、覆盖验证或事务失败，保留上次成功数据和成功来源。可单独记录本次失败。并发读不能看到半新半旧状态。
3. 不以普通upsert加“最后来源”冒充整段覆盖；必须证明旧行没有残留为未记录的另一来源。确需替换时仅限目标股票缓存，不触碰已保存报告、输入快照或冻结交付包。
4. 上游条数/窗口限制、缺失日或复权不连续导致不能完整替换时，应明确失败/不完整，不用尾部成功冒充整段成功。分批请求必须验证覆盖与复权连续性。同厂商发生复权基准变化时同样需要处理旧前缀，不能只比较厂商名称。
5. 来源随实际返回批次进入cache、AI快照和历史；缓存命中不能使用当前进程上一次请求的来源。历史读取保留保存时信息，不回填旧报告。

## 决策二：C同意完整日线以最近已完成交易日为边界

这是明确“完整日线”的时间边界；**同一已完成区间的完整性要求不降低**。不把今天尚未收盘的行情当成完整日线参与默认评分/回测。

- 使用Asia/Shanghai时区和可信交易日历，由B/D明确收盘后厂商发布/可用时间规则。期望截至日由时钟、日历及明确规则确定，不能取数据库最后一天反推“应有多少条”。空/过期日历继续视为覆盖未知。
- 按B报告的9月18日盘中场景，边界应到9月17日：缓存只有9月16日仍缺一根，不能因排除9月18日就判完整。437/439只是B的日历计数记录，本页不将其当作独立实时取数证据。
- 周末/节假日回退到上一已完成交易日。收盘后按明确的可用时间规则推进期望边界；推进后厂商仍缺数据，须报告未更新/失败，不再偷偷退回缓存最后一天。
- 区分请求截止日与实际数据截至日，可使用现有元信息表达；明确的已完成历史区间不改动。若请求涉及当日未完成日线，不得无提示改写用户参数；实际区间/数据截至日须可见并进入保存快照，由D确定对外产品说明。
- 对筛选到有效边界后的行检查日历覆盖、合法值、最小有效条数及预热；不能靠额外的盘中行凑足条数，其他校验及4/2/6精度规则不变。
- 缓存完整可服务不等于实时Provider已经通过；真实冷启动/回源链路仍须单独验证。全部上游失败且缓存不可用时保持既定50001；输入/数据不足等已有错误类别不合并改写。
