### 4.2 一个 HTTP 契约来源

B 负责共享 API 文档/Schema 和数据库契约，D 提供 AI 字段，C 提供计算字段，A 检查是否能直接使用。B/D 给出与指定代码版本对应的 OpenAPI 和实际 JSON：

| 接口范围 | 必须对齐 |
|---|---|
| 股票搜索、data-status | 数组/包装结构、六位代码、来源与新鲜度枚举、覆盖信息、行情日期和刷新时间；失败与无结果分开 |
| 回测 POST | 顶层股票/日期，parameters 五字段，默认值、类型、比例单位及缺省/空对象/null 语义 |
| 回测结果/详情 | trades、三条曲线、实际配置与区间、warmup、initial_equity、算法/语义版本、完整保存快照、data_hash；缺失历史与新完整记录分开 |
| 回测/AI 列表 | 统一确认 `data:{items,total,page,page_size}`、排序、页码边界、空结果 |
| AI POST/详情 | 真实 ID、报告正文和保存的上下文；默认分析独立；行情截至日期来自保存的 market_end_date |
| 错误 | HTTP 状态、业务码、错误包装与页面文案；特别是回测不存在/报告不存在、40001、40003、50001、50002 |

当前报告不存在仍有 `40005` 草稿实现，团队协调目标是回测 `40005`、报告 `40006`。上午由 B/D 将代码、文档、测试、A 注释/mock 同步后再宣布定稿，不让 A 提前假设修正已上线。

B 的 frame_digest、C 的 data_hash、D 的 context_hash、文件 SHA-256 各自记录。HTTP 包装和大输入快照是否默认省略可以由 B/A 定稿，但完整验收读取必须取得当时的完整 C 结果和输入快照，不能丢字段、改类型或二次舍入。

### 4.3 三层检查均通过才称接口对齐

1. **代码层**：团队实际接入同一组可读取提交，C 五字段输入、输出字段和 V1/V2 行为一致。
2. **HTTP 层**：在约定接口基地址请求真实 POST/GET，核对响应包装、数值、空值、日期、错误码、ID、分页；不能只看 Schema 或 mock。运行版本由部署/启动记录和干净 checkout 的 SHA 对应，不要求临时新增版本接口。
3. **浏览器层**：确认 A 的 API 基地址/代理、路径前缀及跨域配置与联调环境一致，页面网络请求打到上述服务，三股流程中的 ID 与数据库相符。

09:30 后变更共享字段，必须在同一协调记录给出变更前后 JSON、受影响成员及新 SHA；消费者适配完成前不合入候选。C 的严格校验不通过时先修 B 传参，不放宽 C 以接纳整个 QuantConfig。
